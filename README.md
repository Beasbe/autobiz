# AutoParser

Собирает данные по заявке (заключения страховщиков, СТС, полисы, письма ФУ, акты, фото и сканы) в общий отчёт:
заполненный шаблон заключения (docx) и таблица «Описание поврежденных элементов и видов ремонтных воздействий» (xlsx).
Реализация этапа 1 из [PLAN.md](PLAN.md).

## Быстрый старт

Нужно: Windows 10/11 (x64 или ARM64), .NET 8 SDK, языковой пакет «Русский» с компонентом **«Распознавание текста»**
(Параметры → Время и язык → Язык и регион → Русский → Языковые параметры). Без него сканы и фото пропускаются,
а текстовые PDF обрабатываются как обычно.

```bash
dotnet build AutoParser.sln
```

Приложение (WPF):

```bash
dotnet run --project AutoParser.App
```

Можно сразу открыть папку заявки: `AutoParser.exe "<папка заявки>"`.

Командная строка:

```bash
dotnet run --project AutoParser.Cli -- process "AutoParser/data/Заявка№10878 26-130531 НТЭ" --out out
```

Прочие ключи CLI: `--template <docx>`, `--no-ocr`, `--ocr windows|linux|yandex|none`, `--ocr-lang rus,eng`, `--verbose` (все варианты каждого поля);
`dump <файл|папка>` показывает распознанный текст, `preview <папка> <поле> <png>` — страницу-источник с подсветкой.

## Linux / Docker

UI (WPF) доступен только на Windows. На Linux работает CLI: OCR-движок подменяется на
Tesseract за тем же интерфейсом `IOcrEngine`, остальной конвейер не меняется.

```bash
# образ содержит Tesseract с русским языком
docker build -t autoparser .

# папки заявок монтируются при запуске (в образ они не попадают — ПДн)
docker run --rm -v "$PWD/AutoParser/data:/data" -v "$PWD/out:/out" \
  autoparser process "/data/Заявка№10878 26-130531 НТЭ" --out /out

# или обёртка: ./run.sh process "/data/Заявка№10878 26-130531 НТЭ"
```

Локально без Docker (нужен .NET 8 SDK + `tesseract-ocr` и `tesseract-ocr-rus`):

```bash
dotnet run --project AutoParser.Cli -- process "AutoParser/data/Заявка№10878 26-130531 НТЭ" --out out --ocr linux
```

Особенности Tesseract-движка: ориентация страницы определяется одним проходом OSD,
распознавание — одним проходом `psm 3` (с фолбэком на `psm 6` для форм со разреженным текстом).
Результаты кэшируются на диске; первый прогон заявки — несколько минут.

Сборка для установки без SDK:

```bash
dotnet publish AutoParser.App -c Release -r win-x64 --self-contained -o publish
```

## Как это работает

```
папка заявки → сканирование + SHA-256 (дубликаты «файл (1).pdf» пропускаются)
            → текстовый слой PDF (PdfPig) → классификация по имени и содержимому
            → OCR только страниц без текста (рендер PDFium 300 dpi → Windows.Media.Ocr, кэш на диске)
            → парсеры: «метка – значение» по словарю синонимов + регулярки с контекстом
            → слияние: веса источников, голосование, уверенность, конфликты, вычисляемые поля
            → таблица повреждений: калькуляция Audatex / акт осмотра
            → docx по шаблону + xlsx
```

- **Локальный OCR** — встроенный в Windows `Windows.Media.Ocr`: работает офлайн и на ARM64, данные никуда не уходят.
  Сам определяет поворот страницы (0/90/180/270) и выравнивает перекос. Результаты кэшируются в
  `%LOCALAPPDATA%\AutoParser\ocr-cache` (очистка — вкладка «Журнал» в приложении).
- **Yandex Vision** (необязательно) — для рукописных актов и плохих фото. Включается, только если заданы переменные
  окружения `YANDEX_VISION_API_KEY` (или `YANDEX_IAM_TOKEN`) и `YANDEX_FOLDER_ID`. Тогда в приложении появляется
  флажок, в CLI — ключ `--ocr yandex`. Документы при этом отправляются в Yandex Cloud (см. риски 152-ФЗ в плане).
- **Валидация важнее OCR**: латиница↔кириллица в ГРЗ, `O→0`/`I→1` в VIN, регулярки ГРЗ/VIN/СТС/полиса/дат,
  пересчёт кВт↔л.с., справочник субъектов РФ (место ДТП → региональный рынок, код ГРЗ — запасной вариант).
  Отсеиваются ГРЗ, VIN и полисы, найденные в контексте виновника.
- У каждого значения есть **источник** (файл, страница, прямоугольник) и **уверенность**. Статусы: OK, Проверить,
  Расхождение, Вычислено, Нет данных, Вручную. В приложении клик по полю показывает страницу с подсветкой фрагмента;
  все варианты поля видны в нижней таблице, значение можно исправить вручную или выбрать другой вариант.

## Настройка без программирования

| Файл | Что внутри |
|---|---|
| `AutoParser.Core/Config/labels.json` | синонимы меток полей («Регистрационный знак», «Гос.номер», …) и маркеры раздела виновника. Новый формат заключения обычно = новые строки здесь |
| `AutoParser.Core/Config/audatex.json` | словарь сокращений Audatex: «НАКЛ Н ЗЕРКАЛО НАР Л» → «Накладка нижняя зеркала наружного левого» |
| `AutoParser.Core/Config/regions.json` | субъекты РФ: коды регионов ГРЗ, города, варианты написания |
| `templates/НТЭ.docx`, `templates/ИРУ.docx` | шаблоны заключений; вид выбирается по имени папки заявки |

После правки JSON нужна пересборка (файлы встроены в сборку).

## Структура

```
AutoParser.Core         net8.0, без UI: всё, что тестируется
  Cases/                сканер папки, дедупликация, номер заявки из имени папки
  Classify/             тип документа по имени файла и ключевым фразам
  Text/                 PdfPig, рендер PDFium, предобработка изображений, IOcrEngine, Yandex Vision, кэш OCR
  Parsing/              LabelValueParser, ContextRegexParser, DamageExtractor, AudatexNames
  Merge/                FieldMerger
  Validate/             ГРЗ, VIN, СТС, ПТС, полис, мощность, даты, справочник регионов
  Export/               заполнение docx-шаблона (OpenXml), xlsx (ClosedXML)
  Pipeline/             CaseProcessor — весь конвейер
AutoParser.Ocr.Windows  WindowsOcrEngine (Windows.Media.Ocr)
AutoParser.Ocr.Linux    TesseractOcrEngine (Linux/macOS, внешний бинарь tesseract)
AutoParser.Ocr          LocalOcr — выбор движка под ОС и ключ --ocr
AutoParser.App          WPF: поля, варианты, превью источника, повреждения, экспорт
AutoParser.Cli          пакетная обработка и отладка
AutoParser.Tests        xUnit: валидаторы, словарь Audatex, «золотые» тесты по папкам из AutoParser/data
```

## Результат на образцах

Заявка 10878 (BMW Z4) сверена с готовым заключением эксперта из этой же папки. Совпали: номер заявки, VIN, пробег,
тип ТС, категория, год, кузов, мощность 190/258,3 (взята из отчёта об истории ТС), АКПП,
«Белый / Акриловая двухслойная», собственник, дата ДТП, «г. Нижний Новгород» (из определения ГИБДД, OCR),
«Нижегородская область», полис со страховщиком. Расхождения:

- марка выдаётся полностью, «BMW Z4 SDRIVE 30I», у эксперта — «BMW Z4»;
- ГРЗ — «Н222ОУ152», у эксперта с пометкой «на момент ДТП б/н, на момент осмотра Н222ОУ152»;
- СТС совпадает, но вместо прочерка в ПТС указывается найденный в полисе ЭПТС;
- дата изготовления в документах заявки не найдена: подставляется год выпуска со статусом «Проверить».

Заявка 27742 (Daewoo Nexia, тотал «МАКС»): заполнены 18 полей из 19, место ДТП не найдено (в документах есть только
адрес осмотра). Таблица повреждений — 32 позиции из акта осмотра, который подшит внутрь `док.pdf`.

Тесты: `dotnet test` — 71 тест. Первый прогон «золотых» тестов идёт около двух минут (OCR), дальше данные берутся
из кэша.

## Ограничения

- Рукописный текст (акт осмотра «РАНЭ-М») локальный OCR не читает — нужен ручной ввод или Yandex Vision (`handwritten`).
- Колонки «Исследование ФО / заявителя / относимость» таблицы повреждений заполняет эксперт (этап 2 — нейросеть по фото).
- Дату изготовления, тип покрытия ЛКП и место ДТП часто нет в документах: такие поля помечаются «Проверить» или «Нет данных».
- `.msg` (письма Outlook) пока не разбираются.
